# 列存浏览与更正工作台

面向「用户保存某条数据的定位链接、按链接发起更正，而底层列存文件会合并、重排、重新分区」
场景的端到端实现。全部基于 Python 标准库，无任何第三方依赖，包含真实列存、定位索引、
并发合并引擎和网页工作台。

## 快速开始

```bash
# 1. 建表演示数据（2000 条物流运单，按大区分区写入真实列存）
python3 -I scripts/init_table.py data_store 2000

# 2. 启动网页工作台
python3 -I webapp/server.py data_store --port 8000
# 浏览器打开 http://127.0.0.1:8000/

# 3. 跑全部测试（20 个引擎/状态测试）
python3 -I tests/test_engine.py
python3 -I tests/test_state.py

# 4. 跑 HTTP 端到端场景（需先起服务，默认找 127.0.0.1:8000）
WORKBENCH=http://127.0.0.1:8000 python3 -I scripts/e2e_demo.py
```

## 核心设计决策：永久逻辑标识 + 可重建的位置映射

链接不能依赖物理行号，因为合并/重排/重分区会让「第 N 行」指向另一条记录。
本项目把**身份**和**位置**彻底拆成两层：

| 层 | 载体 | 生命周期 | 是否进链接 |
|---|---|---|---|
| 逻辑身份 | RID（32 字符 uuid4 hex） | 记录创建即分配，**全局唯一、永不变、永不复用** | 是，链接只含 RID |
| 物理位置 | 定位索引（RID → 段+段内 ordinal+代） | 每代一份，合并时整体重写 | 否，对用户透明 |

- **永久链接** `/#/record/<rid>`（本实现路由为 `/record/<rid>`）：只认 RID，
  引擎在当前代索引里二分定位；物理位置怎么变都指向同一条记录。
- **时间点快照链接** `/snapshot/<gen>/seq/<n>/record/<rid>`（亦兼容不带 seq 的
  `/snapshot/<gen>/record/<rid>`）：固定第 `gen` 代的物理布局，且 delta 只重放到序号 `n`。
  因此快照在保存那一刻就被冻结，之后他人的更正/删除不会污染它；快照超出保留期时返回
  **HTTP 410 GONE** 并显式说明，**绝不**静默重定向到当前的另一条记录。

### 定位索引成本（可量化）

- 每条索引记录**定长 112 字节**：RID 32B + 段名 64B + ordinal 4B + flags 1B + 版本号 8B + 对齐 3B。
  2000 行约 219 KB，与行数严格线性（`tests/test_state.py` 断言了体积公式与线性度）。
- 索引按 RID 排序、`mmap` 打开，定位是 **O(log N) 二分查找**，不需要全量载入内存。
- 写入/合并成本：每次摄入或合并都重写全量索引，**维护成本 O(N)** —— 这是刻意的取舍：
  用合并时一次性的顺序重写，换取读取路径上无跳转、无 B 树维护、无碎片。
- 列存本体按列分 chunk（null 位图 + 类型化二进制 + zlib 帧），查询只解压投影列，
  段尾 footer 记录每列偏移，不读无关列。

### 删除后定位

删除是**软删除墓碑**，不是物理抹除：

1. delta 流水追加 `delete` 事件（带 base_version 校验）；
2. 下一次合并时，墓碑不进段数据，但仍以 `deleted` 标记写入新一代索引，RID 不丢；
3. 扫描结果过滤墓碑，而 `locate(rid)` 永远能查到「该 RID 存在、已删除、归属哪一代哪个段」；
4. 支持 `undelete` 复活：复用同一 RID，版本号继续递增，版本历史不断。

### 历史保留范围

- 保留策略 = **当前代 + 最近 N 个历史代**（默认 N=3，共 4 代），可在 `Table(keep_generations=...)` 调整。
- 超期的代不直接 `rm`，而是移动到 `_orphans/` 隔离区，归属仍可查证，确认无用后再手工 purge。
- 两条 JSONL 日志（系统事件、记录 delta）**永久保留、只追加、每条 fsync**，
  不受代 GC 影响 —— 即使物理快照过期，某条记录「被谁改过、基于哪一版、何时删除」仍可完整审计。
- 时间点快照依赖 delta 序号：物理代过期后该代布局不可读（返回 410），但 delta 日志仍在，
  归属与版本链的审计能力不受影响。

## 并发正确性：合并期间的更正

- 进程内 `RWLock`：浏览/定位走读锁可并发；摄入、更正、删除、合并切换走写锁独占。
- 更正是**乐观并发控制（OCC）**：表单携带 `base_version`，提交时服务端校验
  `base_version == 当前版本`，不一致直接拒绝（`DeltaConflict`），**过期更正不可能覆盖他人新值**。
- 合并全程持写锁：期间到达的更正排队等待；切换完成后它们读到的是新版本号，
  旧 base_version 自然冲突，不会基于旧代写入。
- 跨进程另有 `fcntl` 文件锁保护 manifest 指针切换。

### 映射切换失败后的归属可查

合并采用「暂存目录 + 原子 `os.replace` 切换」：

1. 新一代先完整写到 `staged-gen-N/`（段、索引、manifest 全部 fsync）；
2. 切换前可注入故障（网页上勾选「模拟 manifest 切换失败」）；
3. 失败时暂存目录被移入 `_orphans/failed-swap-*`，事件日志记录 `switch_failed`，
   **旧代原封不动继续服务**；
4. `state.json` 写坏也能从 manifest 链自动重建（有测试覆盖）。

## 目录结构

```
colstore/
  encoding.py    列编码：null 位图 + 定长类型编码 + zlib 帧
  segment.py     列存段：每列一个 chunk，footer 存列偏移，支持列投影读取
  index.py       定位索引：定长记录、排序、mmap 二分、墓碑标记
  journal.py     追加日志 + OCC 版本校验（DeltaConflict）
  locking.py     读写锁 + fcntl 文件锁
  state.py       manifest 代链、原子切换、保留 GC、孤儿区、崩溃恢复
  table.py       表引擎：摄入/浏览/定位/更正/删除/合并/快照
  partitions.py  四种物理布局策略（重排只动物理位置，RID 不变）
  demo_data.py   演示数据集
webapp/server.py 标准库 ThreadingHTTPServer 网页工作台
scripts/         建表、端到端演练脚本
tests/           20 个测试：定位不变性、OCC、删除墓碑、时间点快照、快照过期、
                 切换失败、并发风暴、崩溃恢复、索引成本
```

## 网页上可直接操作的验收路径

1. 首页点任意 RID → 详情页给出**永久链接**和**快照链接**，复制保存；
2. 首页用「合并/重排/重分区」面板依次选三种策略（含随机洗牌），
   再打开保存的永久链接 —— 物理位置（g/seg/ordinal）已变，记录还是同一条；
3. 开两个标签页基于同一版本各自更正：第二个提交收到红色冲突提示，新值不被覆盖；
4. 软删除后链接仍显示墓碑与归属，可一键复活；
5. 勾选故障注入再合并：提示切换失败、旧代仍可浏览、孤儿区出现失败产物、
   事件日志可查，清理后重试成功；
6. 连续合并 4 次以上，最早的快照链接返回 410 而非指向别的记录。
